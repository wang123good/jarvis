# JARVIS 项目协作画像 v0.1.0

2026-11-18 用户确认方案并授权落地。仅适用于 JARVIS；不是全局人物画像或常驻记忆服务。

## 读取与应用

在项目根目录运行 `python jarvis/user-profile/read_profile.py`。该只读工具核对发布哈希、来源哈希、项目范围与条目状态，输出可选条目。管家再按 conditions 和 exceptions 判断是否与本任务相关；出现次数不代表批准。文件异常时停止使用画像，仍遵从当前指令和项目入口。

profile.json 是已批准约定的发布快照；source 指向事实来源，来源变化时旧快照不继续自动应用。P3 是治理约定引用，不是个人特质。candidates.json 仅为候选，不参与读取。schema.json 定义两个数据文件的结构；changes.jsonl 是追加式发布日志，approval-0.1.0.json 保留本次批准范围及来源缺口。

## 更新、暂停和撤销

1. 管家可记录必要的候选及实际来源，默认 status=candidate，批准字段为空；没有可核对证据时不记录推测性长期条目。临时要求只在任务卡记录，不自动转画像。
2. 集中向用户提交具体差异、范围、例外和当前 profile.json 的 SHA-256 基线。用户批准后，核对基线未变化再写入；基线变化须重新核对差异。
3. 发布前保存旧 profile.json 到 versions/，以版本号和哈希命名；修订递增版本，写明 supersedes，追加 changes.jsonl 的旧/新哈希、批准来源与条目 ID。单个写入流程，先落数据后追加日志；中途失败时读取器会拒绝哈希不匹配版本，修复后再交付。文件哈希是完整性检查，不是防篡改或访问隔离。
4. 用户明确纠正、暂停或撤销时，本会话立即停止使用相应条目；按用户授权更新状态并发布，旧记录保留为依据。一般偏好变化需集中确认。临时例外不改长期版本。新旧指令冲突时以当前要求为准，不能用画像覆盖当前要求。
5. review_after 为空代表未设自动复核期限，不代表永久正确；遇到反例、来源变化或用户指出过时时复核。到期条目暂停自动读取，重新确认后更新期限。

专业背景、职位、人格不推断；主动提供的相关背景须单独确认。授权边界仍由项目指令管理。跨项目应用、历史会话扫描及自动整理均未启用；知识库管理员仍由用户手动触发。

## 验证与回退

verification.json 记录本地检查。后续三个真实任务在任务卡记录使用条目、用户纠正、额外确认；新会话读取、真实纠正和效率收益尚待验证，不自动创建任务或定时器。

入口接入前备份位于 `jarvis/backups/user-profile-deployment/`。回退时先核对后续修改，仅移除本次画像入口和 defaults 中 user_profile 配置，保留画像与批准证据。不要直接覆盖含后续编辑的文件。
