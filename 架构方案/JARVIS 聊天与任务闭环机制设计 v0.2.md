# JARVIS 聊天与任务闭环机制设计 v0.2

- 日期：2026-11-20（Asia/Shanghai）。
- 状态：2026-11-20 用户认可并授权落地；运行规则已接入，实施结果待用户验收。恢复验证范围见文末实施记录。
- 任务：JV-20261120-TASK-MODE，契约修订 2。
- 范围：聊天/任务识别、目标契约、规划价值审查、可人工恢复的执行记录、验收与变更、知识收尾及 Skill 判断。
- 版本关系：本文是架构 v1.6 的专项补充设计，不取代总览，不递增 GitHub 发布版本。
- 来源：用户最初设想、三项补充及现行架构/职责/模板；上一轮草案保留于本地任务目录。原设计阶段不改运行入口；随后用户明确要求落地，本轮实施范围及证据见文末。本文所述“待批准”保留设计阶段语境，已实施项以文末及现行规程为准。

## 1. 结论、价值与本次自查

推荐建立“按意图进入任务、按契约规划、按目的审查编排、按证据推进、按检查点人工恢复、按用户验收闭环、按复用价值沉淀”的机制。

价值在于让用户能够知道：当前在做什么、为什么做、做到了哪里、是否达标、中断后从哪里继续、何时可以结束聊天。代价是状态维护和验证开销，所以记录粒度应服务于恢复和验收，不能为形式增加步骤。

| 上版不足 | 本版修订 | 可核对要求 |
|---|---|---|
| 仅提检查点，未交代异常中断后怎样接续 | 增加环节记录、执行前后落点、人工恢复协议和未知结果核对 | 换聊天也能凭任务 ID 找到下一步；没有证据不能假定动作没发生 |
| Skill 判断偏重重复流程 | 引入已确认画像、实际工作需求、输入变化和维护收益 | 明确采用何种依据；没有职责数据不推断；允许结论为无需 Skill |
| 有计划但缺编排自身的价值验收 | 增加逐步目的、下游用途、删除测试及评审结论 | 每个保留环节都能解释对目标、必要风险控制或验收的作用 |
| “已完成”混合业务、笔记与长期发布 | 分离业务验收、收尾、Skill 决定及关闭判定 | 不会因笔记完成掩盖业务失败，也不会因 Skill 延期无限挂起任务 |

## 2. 与既有架构的关系

基线：[架构 v1.6](./JARVIS%20管家%20Worker%20Skill%20与知识库管理员架构设计%20v1.6.docx)、[管家职责](./JARVIS%20管家Agent职责定义%20v0.1.md)、[Agentic 设计笔记](./JARVIS%20Agentic%20架构设计笔记.md)、[实现差异清单](./当前实现与架构差异清单%202026-11-20.md)。运行入口仍为 [AGENTS.md](../AGENTS.md)。

| 架构组件/约定 | 本设计如何衔接 | 状态边界 |
|---|---|---|
| 管家是任务闭环所有者与控制面 | 维护任务卡、规划评审、状态、恢复决策和总体验收 | 不新建独立常驻服务，不转移最终责任 |
| Worker 是临时有界执行实例 | 只在收益明确时使用；绑定父任务与契约修订，返回结果及恢复信息 | 不为编排而创建 Worker；Worker 完成不等于任务验收 |
| Skill 是可复用能力包 | 封装适用流程、判断、工具和验收；任务状态仍由管家持有 | Skill 不成为第二份任务状态，不自动获得新权限 |
| 知识库管理员手动离线、草稿/diff/批准应用 | 任务验收后根据具体收尾授权处理限定来源 | 自动触发及自动保存总结是待批准的扩展，现行手动规则继续有效 |
| task_id、contract_revision、失败账本、检查点 | 在其上细化 plan_revision、step_id、attempt_id 和恢复协议 | 继承父任务累计失败，不重置旧预算 |
| 本地画像只用已确认条目 | Skill 决策读取相关且已确认的偏好/职责依据 | 不能从任务主题或资料推断职业；不扩大画像收集范围 |
| 文件/指令承载控制面 | 采用最小文件记录和人工重启入口 | 不宣称数据库事务、硬锁、自动恢复或精确一次执行已经实现 |

v1.6 DOCX 含内层 jarvis/ 旧路径；本设计按 V1.1.0 目录重构使用 config/、templates/、agents/、scripts/、.local/，不恢复旧路径转发。现行文档中注册表“为空”的历史描述不证明本机接入正常；本轮配置的注册表路径未找到，应标为不可用，而非空表已核验。

## 3. 聊天、任务与会话标题

区分依据：是否要求 JARVIS 对一个可描述的交付结果负责。话题跳跃不等于聊天，长时间讨论也不一定是任务；方案探索可以是任务，其验收对象是探索范围、证据和决策质量。

1. 只有唤醒且意图不明：询问聊天还是推进任务。
2. 明确交付要求：直接形成契约草案，不重复问二选一。
3. 明确闲聊：正常交流，不机械建卡；产生交付要求时提出切换。
   - 2026-11-20 实测补充：聊天中“要不要一起搭一个工具，有兴趣吗”包含建设动作和产物，是潜在任务转折；必须询问先聊可行性还是正式启动，不能只追问技术参数或擅自判为闲聊。明确执行指令直接起草契约；明确假设/测试仅作为测试，不启动被演示业务。
4. 恢复旧任务：按任务 ID 或唯一明确上下文恢复，不另建空白任务。
5. 一个聊天默认一个主任务；新目标独立可验收时另立关联任务，不从插话推定扩充目标。

2026-11-20 用户批准更新：用户明确建立真实新任务并首次建卡时，在所属项目创建以任务名命名的专属对话，回读名称与项目后绑定任务卡；待澄清/待复核也可先分流。修订、返修、恢复复用原绑定，接收交接不再次创建。保留来源对话，不删除旧消息；建会话不替代业务复核。创建未知先查证，已创建而命名/关联失败则修复已有对话；工具状态与侧边栏视觉分别核验。具体字段、交接包和异常流程以当前任务闭环规程为准，状态以任务卡记录为准。

现行专属对话标题格式按 AGENTS.md E11 执行，使用「任务名称【当前状态】」。

## 4. 任务契约与授权

由管家起草，用户只确认关键问题；简单任务用简卡，需追踪和恢复的任务采用持久任务卡。完整卡的最小字段如下：

| 分组 | 必需信息 |
|---|---|
| 身份 | task_id、名称、当前聊天及关联聊天、契约/计划修订 |
| 目标 | 原始意图、场景、预期价值、明确结果、不做事项 |
| 验收 | 每项交付的标准、方法、证据位置、检查者、必需/可选项 |
| 输入 | 来源与版本、已知事实、假设、缺口和依赖 |
| 授权 | 允许的读写/外部动作、知识收尾策略、约束及用户依据 |
| 计划 | 子任务目的、依赖、方法、产出、验证、价值审查记录 |
| 预算 | 主动执行上限/检查点、截止时间、等待边界、重试、分支及可测费用 |
| 执行 | 环节状态、结果、证据、尝试、异常、副作用和检查点 |
| 恢复 | 中断原因、真实活动、已完成/未确认动作、剩余预算、下一安全动作 |
| 收尾 | 自检与用户验收、修订、笔记、Skill 决定、关闭条件 |

实质执行前提交判断、契约和组织方式，经用户复核启动；用户明确要求的具体返修可直接作为本次修订依据，不对相同动作递归请示。当前任务卡是单一当前状态入口，历史事件/证据保留；标题、旧对话摘要或 Worker 报告都不能单独覆盖它。

## 5. 规划编排的记录与价值评审

### 5.1 最小计划

每个子任务记录：step_id、目的及对应验收项、输入/依赖、动作、输出、下游用途、完成证据、执行者、预算、可重做性及副作用。只有真实依赖才连线；能直接完成时不用 DAG，不为了画图或模仿框架拆分。

默认直接执行。只有隔离、并行或独立复核的收益足以覆盖沟通和整合成本时才委派，并记录理由。多个目的相同且产出重叠的环节优先合并。

### 5.2 执行前必须自审

管家留下简短、可审核的结论，而不是内部推理全文：

| 审查问题 | 判断方式 |
|---|---|
| 为什么需要这一步？ | 指向具体目标、验收要求、真实依赖或必要风险控制 |
| 删除它会损失什么？ | 无可说明损失则删除或合并；必要验证/恢复记录也可以构成价值 |
| 谁会使用它的产出？ | 交付用户、后续步骤或证据/恢复核对；无人使用的报告不保留 |
| 是否有更短的路径？ | 比较直接完成、复用现有成果、串行/并行及工具成本 |
| 是否能够验收并恢复？ | 有完成条件、证据和失败后下一步，避免只有动词没有结果 |
| 组织收益是否真实？ | 不按 Worker 数或步骤数衡量先进性；不凭形式制造阶段 |

每一步结论为保留、合并、删除、延期，附简短理由；计划整体结论为通过或需修订。未通过先改计划再启动依赖执行。风险或复杂度高时才考虑独立评审，不强制再建一个评审 Agent。

用户复核目标契约及组织方式，管家负责内部计划质量；不要求用户逐项审批所有子步骤。plan_revision 随内部计划变更增加，记录原因与受影响步骤；影响目标/范围/验收/预算/组织授权时同时修订 contract_revision 并复核。变更后受影响后继步骤暂停或待重验，不能沿用过期证据。

### 5.3 例：避免无价值环节

“评审并补全方案”可以是：核对基线 → 形成设计 → 场景检查 → 交付。若另设多个 Agent 各写同一份摘要，再开一轮只改写措辞的汇总，既没有独立证据也没有验收用途，应合并或删除。

## 6. 状态、环节结果及持久记录

### 6.1 状态不能混用

- 任务状态：待澄清、待复核、执行中、待用户决策、已暂停、已交付待验收、已验收、已取消、失败/停止。新细分状态是建议，落地时与现行模板同步。
- 环节状态：待执行、执行中、已执行待验证、已验证、失败、阻塞、结果未知、已失效、已跳过。
- “已跳过”要说明为什么不再需要；依赖不会因上一步标跳过就自动满足。
- 中断单独记录原因与时间。上次记录执行中而本次无可靠活动证据时，先标“需恢复核对”，不直接假定失败或完成。
- 业务验收、知识收尾、Skill 决定分别记录；只有被验证的必要结果才能满足父任务验收。

### 6.2 最小恢复材料

建议每项需恢复的任务使用 `.local/tasks/<task_id>/`：

| 文件/内容 | 职责 |
|---|---|
| contract.md | 最新契约、计划、价值评审、当前状态、最近检查点及下一步 |
| events.jsonl（或等价追加事件表） | 关键状态变化、尝试、动作结果、验证和用户决定；保留历史顺序 |
| evidence/ 与 artifacts/（必要时） | 按 run_id/attempt_id 定位的证据或产物；已有文件可直接引用，不机械复制 |

小任务允许把计划、事件表及检查点合并在一张卡内；不强制拆成多个文件，不为状态管理建立大型日志系统。记录必要事实与结论，不保存私密推理、无关隐私、密钥或整段宿主注入。

环节记录至少包括：task_id、contract_revision、plan_revision、step_id、attempt_id、时间、执行者/实际实例、输入基线、动作及状态、输出路径/必要版本哈希、验证结果、错误、外部回执、重试用量、依赖满足情况和下一步。

### 6.3 何时记录，如何应对突然中断

1. 有副作用或成本的动作开始前，先记录意图、目标对象、输入基线、授权依据、尝试 ID、是否可重复及查证方法。
2. 工具返回后立即记录真实结果、回执或“未知”；结果验证后才标已验证并更新下游状态。
3. 阶段结束、等待用户、委派交接、计划变更、主动暂停和交付时保存检查点；长步骤在可恢复的边界分段记录。
4. 突然退出可能来不及写最终检查点。因此恢复不能只信记录：必须核对实际文件、外部状态和活动实例；“缺少成功记录”不等于“动作未发生”。
5. 外部服务支持幂等键时才使用其真实能力；不支持时通过先查询后决策减少重复，不宣称精确一次执行。
6. 预期记录路径不可写时，停止依赖可靠记录的副作用动作，说明限制；不要边执行边积累无法恢复的未知状态。

写入设计采用单一管家维护当前任务卡、追加历史；更新前核对基线，临时文件校验后替换当前快照。证据使用独立 ID，冲突不覆盖。文件替换不能提供跨文件事务、跨进程锁或宕机后零丢失保证；事件与快照不一致时先按事实核对再形成恢复事件。

## 7. 人工重启与恢复协议

### 7.1 人工入口

用户可在原聊天或新聊天说：“JARVIS，恢复任务 <task_id>”，也可提供任务卡路径。任务卡即使聊天被关闭也应可定位；若本地卡和必要产物已删除，则如实报告无法完整恢复，不假装记得全部进度。

“恢复”授权在原契约仍适用时继续未完成工作，不自动重置预算、重新发送外部请求或重放已完成步骤。多个候选任务时仅让用户选定目标，不扫描全部旧聊天。无守护进程监视或自动唤醒承诺。

### 7.2 恢复顺序

| 顺序 | 核对/动作 | 未满足时 |
|---|---|---|
| R1 定位 | 读取最新契约、计划修订、事件、检查点及关联产物 | 缺材料时说明缺口；仅做必要重建，不编造历史 |
| R2 防重复 | 查询仍在运行的工具/Worker/外部作业，核实当前写入者 | 不能确认旧执行结束时不启动重复或冲突写入；等待或请求决策 |
| R3 查事实 | 逐步核对已完成产物、验证、输入版本及外部回执 | 漂移标待重验；结果未知先查询，不能盲目重试 |
| R4 复核边界 | 核对授权、目标、依赖、截止时间及父任务剩余预算/重试 | 到期、超限或条件变化时请求修订；未知用量不填 0 或默认全额 |
| R5 选恢复点 | 复用有效结果，重验受影响结果，选第一个安全且依赖满足的未完成步骤 | 没有安全动作则进入待决策，不从头重跑 |
| R6 留痕并续作 | 写恢复批次、事实核对结论、保留/失效步骤和下一步，再执行 | 原范围内直接继续；仅新增关键决策需要用户复核 |

已验收任务收到“恢复”时先判断用户是要查看结果、返修还是新增需求，不能擅自重新执行。已取消任务明确要求恢复后，仍要检查旧授权和预算是否有效。

### 7.3 恢复交接信息

每次停顿提供简短可复制入口：任务 ID/卡片路径、当前契约及计划修订、最后已验证步骤、未确认动作、实际产物、剩余预算或未知项、阻塞原因、下次首个核对动作。无须把整段聊天交给下一次执行。

## 8. 执行、预算、验收及追加要求

经契约复核后，在授权内连续规划、执行、验证、修正。默认护栏沿用 config/defaults.json：直接模式优先；必要 Worker 最多 2 个、并发最多 2 个；同类失败首次之外最多追加 2 次；探索最多 2 条分支；约 20 分钟主动执行做收敛检查，均不是宿主硬限额。

完整任务明确主动执行上限、日历截止时间、外部等待边界和费用约束；等待用户与主动执行区分，预算只记录实测值。两次检查连续无进展、达到尝试上限、预算耗尽、缺输入/权限或无法验证时，保存状态并交部分成果及决策选项。

验收用“交付项—标准—方法—证据—用户决定”逐项核对。自检通过进入待验收；沉默或继续讨论不自动表示通过。任务要求人工验收时必须等明确决定。

原标准未达属于返修，同一失败累计；新增目标/范围/标准/预算应展示差异及影响，由用户认可修订。同一目标增补保留任务 ID；独立目标建立关联任务。受影响工作包暂停并核验，未受影响的独立准备可继续。

## 9. 三层知识收尾

按现行 project/domain/resource 定位：项目总结位于工作记录，领域知识位于 wiki/主题，资源位于 wiki/参考资料。三层是知识用途，不是每次必须输出三篇；只记录新增且有价值的信息，优先链接、去重。

依据收尾实测反馈修订：成果明确验收后，先确认本任务笔记选择（不整理/本地/知识库），已有明确选择不重复询问；未答不自动整理，不提前宣布全部收尾。仅同意本地整理时准备任务总结及必要领域/资源候选；限定来源、路径、是否允许写入、已有文件冲突处理及停止条件。没有新增知识则注明跳过。

目前知识库管理员仍是手动离线角色；自动触发和自动写入限定总结/草稿，需要落地时明确批准并同步规则。正式 wiki 覆盖、规则、正式经验和长期能力按批准差异及基线应用，不由业务验收自动授权。用户明确不用整理则跳过；不自动扫描其他聊天、其他项目或生成日报周报。

## 10. 结合用户画像判断 Skill，而非把所有任务 SOP 化

### 10.1 判断依据及其优先级

1. 当前用户明确要求，以及任务的实际输入、目标变化与验收证据。
2. 根目录 up.json 中当前启用、scope=JARVIS、status=approved 且与本任务相关的偏好；职责信息仅在用户明确提供并确认、且本项目有合法可用的记录时采用。
3. 已核验的同类任务复用需求、已有 Skill、适用边界和维护成本。

画像候选、过期/撤销条目及从话题推断的职业不能作为决策事实。用户职责或喜好未知时标未知；只有其答案会改变本次是否固化的判断时才询问。不为了完成 Skill 判断补造画像，也不把本任务临时要求自动写成长久偏好。

本轮画像读取仅返回昵称及空的已确认偏好列表，没有可用工作职责依据；本文不据此猜测用户职位或业务。未来若需职责字段或画像机制扩展，应另行设计和确认，而非偷偷新增 schema 字段。

### 10.2 决策表

| 任务特性与用户需求 | 优先沉淀方式 | 说明 |
|---|---|---|
| 偶发、探索性强、目标随情境变化，预计不复用 | 项目总结或主题知识 | 不制作 Skill，也不强行写 SOP |
| 用户反复需要某类交付，输入输出和步骤稳定 | 模板、脚本或流程 Skill | 先比较最轻的复用形式与维护收益 |
| 输入/目标变化大，但澄清、判断框架和验收稳定 | 有边界的判断型 Skill 候选 | 固化问题、分支、证据阈值及退出条件，不预设结论 |
| 只有部分步骤稳定 | 固化稳定片段，保留管家情境决策 | 不把整项任务硬塞进一条固定流程 |
| 用户偏好人工讨论，或职业场景依赖大量隐性判断 | 知识/检查清单，或需要交互的 Skill | 自动化程度服务于用户需求，不以减少对话为唯一指标 |
| 已有适用 Skill | 直接复用或提出改进 | 不重复创建；是否更新仍需验证与授权 |

Skill 可以包含方法和条件判断，不必等同固定 SOP；但若连触发条件和成功标准都不稳定，就不应过早包装。

### 10.3 记录及确认

每项任务收尾记录结论：不建议、建议复用已有、建议模板/脚本、建议部分固化、建议新 Skill、暂缓待证据。依据至少写：用户相关需求及来源、输入/目标变化、稳定可复用部分、预期收益/成本、适用边界及不确定项。

最终向用户集中报告一次判断。不值得固化时说明无需 Skill；有价值时再询问是否制作，用户仍可主动要求。用户不制作或延期不阻塞本任务结束。Skill 制作是关联任务，使用真实 skill-creator 指引，经过正常、边界和失败场景验证及人工发布确认；不是验收业务成果后自动上线。

## 11. 关闭条件

业务目标已验收或明确取消/停止；新增要求已完成或明确转交；没有活动执行或未核实副作用；必要产物及恢复入口已交付；笔记完成或明确跳过/转交；Skill 决定已记录。满足后可报告“本聊天可以结束”。

任务卡及相关产物的留存与聊天界面分开。结束聊天不等于归档或永久删除；清理仍需对应授权，并再次核对活动状态。保留当前聊天，不能为满足关闭条件主动中断其他工作。

## 12. 场景检查与待实施验证

以下仅为本次设计层逐项检查，不代表运行实验通过。

| 场景 | 设计应有的处理 | 检查结果 |
|---|---|---|
| 唤醒无意图 / 直接任务 / 聊天转任务 | 按第 3 节区分，避免重复询问 | 已定义 |
| 子任务无人使用且删掉无损失 | 价值审查删除或合并，不派发 Worker | 已定义 |
| 规划变化使后继输入失效 | 升计划修订，暂停后继并重验，必要时重审契约 | 已定义 |
| 已验证两步后应用退出 | 人工按 ID 恢复，核对事实后从安全未完成步骤接续 | 已定义 |
| 外部写入成功但未记回执就中断 | 标结果未知，查外部状态；无法查明则待决策 | 已定义 |
| 旧 Worker 或外部作业仍运行 | 不重复派发，不启动冲突写入 | 已定义 |
| 记录称完成但产物被人工修改 | 标待重验，保护修改，不直接覆盖 | 已定义 |
| 记录文件无法写入或多写入者冲突 | 暂停依赖可靠状态的副作用动作，核对基线 | 已定义 |
| 中断前已耗尽重试/预算，或用量不明 | 不重置额度；核对或请求新增预算 | 已定义 |
| 新聊天恢复但缺卡片/多个同名任务 | 请求必要定位或说明缺失，不假造记忆 | 已定义 |
| 画像职责未知或只有候选 | 标未知，不推断；必要时仅问影响决策的问题 | 已定义 |
| 变化大且偶发的任务 | 可只留知识，不转 Skill/SOP | 已定义 |
| 输入变化但评价方法稳定 | 只提有边界的判断型 Skill 候选，不固定结论 | 已定义 |
| 验收退回/追加需求 | 区分返修和修订，保留历史及失败累计 | 已定义 |
| 业务通过但笔记冲突/Skill 暂缓 | 收尾独立管理；明确转交或跳过后可关闭 | 已定义 |

落地后至少真实试验：纯聊天识别；轻量任务；包含新增要求的完整任务；无副作用步骤间人工中断并跨聊天恢复；在可控副本中模拟“写入后未记完成”；核对旧执行仍活动时不重复派发；无画像职责时的 Skill 不固化判断。只用测试副本和获准动作，不拿真实对外写入做破坏实验。

通过标准：关键步骤可追溯、已验证有效结果可复用、未知副作用不盲重放、预算不清零、每步有目标用途、画像无越权推断、知识/Skill 未自批发布。时间和成本只报告可测结果。
