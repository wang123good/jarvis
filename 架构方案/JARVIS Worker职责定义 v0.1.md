## 职责评审

架构中“执行工作包并返回证据、按需派生、不直接检索知识库管理员/Obsidian”的定位正确，足以支持通用临时 Worker。要可执行，还须补齐工作包接受检查、自主执行边界、状态返回和交接机制。无需先为每种任务创建长期 Worker。

| 职责 | Worker 应做什么 | 边界 |
|---|---|---|
| 接受工作包 | 检查目标、输入、输出、验收、读写范围、预算和依赖是否足够；明确缺口 | 不重定义用户总目标，不把缺失条件猜成已授权 |
| 子任务内规划与执行 | 在工作包范围内安排步骤，选用管家允许的实际工具与 Skill，完成代码、分析、文档或检查 | 可调整局部方法，不扩展业务范围；Skill 可缺省，不虚构已有能力 |
| 校验与证据 | 检查产物与引用，执行适合的验证，保留可复现命令、结果、路径和必要哈希 | 自检不代表管家验收；不宣称未运行的测试通过 |
| 进展与异常返回 | 完成时汇总；重要阻碍及时说明，区分 partial / blocked / failed | 证据不够就报告，不绕过管家去访问全库或找用户审批 |
| 交付与移交 | 返回产物、状态、变化文件、风险及建议；补充管家指出的问题 | 不自行合并其他 Worker 结果，不发布长期资产；生命周期由管家结束 |

## 管家必须提供的最小工作包

任务 ID、parent_task_id、contract_revision、work_package_id、实际 agent_id、目标、必要输入及来源、输出位置与格式、验收标准、允许读写路径、工具/Skill、时间/重试/并发预算、依赖、停止条件、返回契约。无相关经验时明确写“无”，不强行塞入历史材料；宿主实例尚未创建时不编造 agent_id。

实质任务须先经过管家的事前契约复核；复杂度、完整闭环和委派分别判断。完整闭环不要求使用 Worker，使用 Skill 也不排斥有明确收益的委派。

Worker 接收到的项目入口可能描述管家角色，但当前明确工作包将其限定为 Worker。管家必须明确角色，避免多个实例都把自己当最终负责人；仍遵守更高层工具与宿主规则。

## 默认执行约束

- 仅读取管家提供或显式允许的输入，不直接检索 Obsidian、知识库管理员或无关历史会话；缺少资料向管家说明。
- 默认不派生下级 Agent，不接管管家职责。确需进一步分工时提出理由，由管家决定。
- 对共享工作区采用明确、尽量不重叠的写入范围；不得覆盖其他人的修改。读到超出范围的内容不自动意味着可使用。
- 同类失败按父任务 failure_key 累计，返修、重派和换人不清零；子包上限取本包额度与父任务剩余额度的较小值。默认检查点约 10 分钟，同类失败额外重试最多 1 次、后代 0；受管家总预算约束，均为软约定。
- 契约变化后暂停受影响执行，返回已发生及未知动作；旧结果按新契约重验后才可采用。未知副作用不盲目重放；预算将耗尽、依赖缺失、需要跨界或风险升级时交回管家。
- 不扩大权限、不修改审批或沙箱、不发送外部消息、不启用新增计费服务，不删除原始证据。
- 可以提出可复用方法或 Skill 候选，不维护长期画像，不直接更新正式经验、Skill 注册或可信知识。
- Worker 间协作若任务确有需要，须由管家明确协作范围、共享证据与冲突处理方式；当前首版不默认开启。

## 返回契约

```json
{
  "task_id": "由管家分配",
  "parent_task_id": "父任务 ID",
  "contract_revision": 1,
  "work_package_id": "稳定工作包 ID",
  "agent_id": "实际宿主实例 ID",
  "failure_events": [],
  "actions": [],
  "status": "completed | partial | blocked | failed",
  "summary": "完成了什么",
  "artifacts": [],
  "checks": [],
  "findings": [],
  "blockers": [],
  "remaining_risks": [],
  "changed_files": [],
  "next_action": "建议管家做什么"
}
```

completed 只代表工作包执行完成，不代表管家已接受，更不代表用户已确认。管家核对产物、关键检查与工作范围后作出接受、返修或停止决定。

failure_events 返回失败类别、尝试序号、原因与证据；actions 返回动作目标、未执行/已执行/未知及证据。管家维护整体失败账本与续作检查点。结束按宿主能力完成或停止；没有销毁工具时不声称已销毁，路径约定不构成硬访问隔离。

## 适用与不适用场景

适合：独立检查、可并行的数据提取、边界清楚的代码改动、隔离上下文的分析。不适合：一句话答复、紧密依赖主任务且立即阻塞下一步的小操作、依赖大量未经整理背景的模糊任务。

既有 `experiments/W1/steward-recheck.json` 记录单 Worker 链路及缺失输入脚本场景；负向结果是校验脚本行为证据，不证明 Agent 全面恢复。`jarvis/tasks/JV-20261118-009-verification.json` 的恢复场景为静态推演，且其中“无统一审批关卡”已由当前事前复核规则替代。不能凭此推断多 Worker 并行、强权限隔离、自动恢复、长期自主运行或成本优势已验证。
