# JARVIS Agentic 架构设计笔记

## 定位

JARVIS 是“项目主会话管家 + 临时执行 Worker + Skill 能力库 + 离线知识库管理员 + 任务经验注册表”的个人 Agentic 协作方案。本文按 2026-11-20 当前实现对齐，完整架构见 v1.6；原 v1.5 及更早版本保留为历史。

管家角色通过 AGENTS.md 持续维护，不是独立常驻进程；Worker 为具体工作包按需创建；Skill 负责复用方法；知识库管理员（原图书管理员）手动离线整理，不参与实时任务。以下角色边界属于指令约定，不能据此声称硬隔离或自动调度已实现。

## 关键决策

| 组件 | 定位 | 边界 |
|---|---|---|
| 管家 Agent | 长期规划与决策主体 | 负责目标、计划、上下文、调度、观察、重规划和交付 |
| Worker | 临时执行实例 | 只承接有边界的工作包，不持有长期记忆 |
| Skill | 可复用能力包 | 负责流程、脚本、样例和验收，不管理任务状态 |
| 知识库管理员 | 手动请求或已批准任务收尾触发的离线角色 | 使用指定来源，产出草稿与 diff，按批准变更应用；无后台监听 |
| 经验注册表 | 规划输入 | 管家读取后写入 Worker Context Pack |
| Obsidian | 人类可读知识库 | 管家检索并裁剪上下文；Worker 不直接访问是职责约束 |

## 运行闭环

```text
目标
→ 读取本地画像并做必要输入盘点
→ 查询任务经验注册表
→ 判断复杂度、闭环方式与委派收益
→ 形成契约并提交事前人工复核
→ 经复核后组织执行与必要任务依赖
→ 装配 Context Pack
→ 管家执行或派生 Worker
→ 观察结果与证据
→ 验收、重试或重规划
→ 保存任务证据
```

## 自进化

**能力进化**

```text
任务证据 → 复盘 → Skill / 知识候选 → 回放验证 → 人工确认 → 版本发布
```

**用户认知进化**

```text
明确昵称或请记住 → 根目录 up.json 已确认条目
其他观察 → candidates → 用户确认 → preferences
```

知识及经验保留来源、适用范围、状态和必要版本证据；本地画像按 `docs/user-profile.md` 保存必要来源并安全更新，不再使用旧分层画像或外部发布快照。候选不因一致证据自动生效，个人 up.json 不提交 Git。

## 任务经验注册表

首版状态采用：

- **已闭环**：结果与目标基本一致，可重复复用对应 Skill。
- **有待完善**：结果可接受，但存在明确不足，需在新任务中继续完善。

状态由知识库管理员建议，人工复核确认。按任务名称、签名、目标和适用范围筛选，再按调用频率降序、更新时间降序、稳定 ID 升序排列；未知频率不编造。正式经验必须关联真实 Skill，普通知识无需强制关联；当前正式注册表为空。

稳定字段示意如下，均为占位设计，不代表已有正式条目或已安装对应 Skill：

```yaml
experience_id: exp-2026-001
task_name: Agent架构评审
task_signature: review-agent-architecture
objective: 评审架构方案的可实施性和风险
status: 已闭环 | 有待完善
status_suggestion: 知识库管理员建议
human_review: approved | needs_changes
call_frequency: null  # 尚无实际调用记录
last_updated: 2026-11-17
evidence_refs: [session_id, artifact_path, test_result]
applicability: [JARVIS, 本地Codex, 架构评审]
skill_links:
  - skill_path: 待核对真实SKILL.md
    version_or_hash: 待核对
```

注册表承担间接输入职责。Worker 不直接调用知识库管理员，也不直接读取全量 Obsidian；由管家筛选后写入工作包。当前 query_experience.py 仅提供部分字段过滤与排序，目标适配、证据和 Skill 版本由管家核对；数值频率和 ID 尾号的实现假设仍有限制，不能将上述占位记录直接交给脚本执行。

## Agentic 特性

- 显式目标、验收标准和风险等级。
- 任务卡、依赖、状态、检查点和停止条件，均由指令和文件维护。
- Worker 输入输出契约及结构化返回。
- 实际工具能力核对、权限与副作用检查；未知结果先查证再重试。
- 执行轨迹、人工审批、失败重试和重规划。
- 产物、过程及验收证据分别检查；尚无通用自动轨迹评测器。

任务卡使用 task_id 和 contract_revision；工作包绑定父任务修订，变更后暂停受影响执行并重验旧结果。失败按父任务 failure_key 累计，重派不清零。默认直接执行，Worker 最多 2 个、并发 2，同类失败追加重试最多 2 次，探索最多 2 分支，约 20 分钟检查点；均为软护栏。任务状态与经验两态分开，自检不等于用户验收。

## 知识库与环境

当前目录为 `01 草稿`、`02 工作记录`、`03 wiki`、`04 模板`、`05 规则`、`06 归档`、`99 附件`。任务总结、日报、周报分别存放，日报周报由用户手动触发；对话直接使用 `06 归档/YYYY-MM-DD_任务名称_对话名.md`，不建多层会话目录，不保存来源 JSON 或运行日志。

`scripts/init_vault.py` 创建缺失目录、9 个模板及导航并保护已有文件；软件自动安装、首次呼叫准备与恢复仍是设计。检索配置保留 project/domain/resource 技术层标识，不代表旧顶层分类。迁移自检与限制见 `jarvis/knowledge-runs/VAULT-20261120/run-report.md`。

## 安全边界

- 知识库管理员默认限定来源，草稿先行，正式写入前复核 diff 和基线。
- 管家不能自行扩大 Worker 权限。
- Worker 不跨项目读取经验。
- 用户画像只按明确保存授权或候选确认更新，不推断专业背景，不以一致证据代替用户确认。
- 不自动归档、生成日报周报或发布 Skill；新增长期能力须另行提案与批准。
- 对话清理区分界面归档、永久删除和磁盘核验；仅在明确授权范围内执行，用户要求不整理时跳过 Obsidian。

## 待验证技术点

- 独立 Agent 自动读取完整 Session。
- 命名 TOML Agent 的发现和调用。
- Worker 权限、工作区和审批隔离。
- Hooks 或 Automations 的幂等触发。
- 大规模 Obsidian 检索和索引性能。
- 知识库管理员状态建议的准确率。
- 频率排序对任务质量的长期影响。

## 可继续完善

1. 从单频排序扩展到“相关度、状态、时效性、成功率、频率”综合排序。
2. 增加经验完备度评分和具体不足分类。
3. 建立 Experience-Skill 多对多映射和版本约束。
4. 增加经验去重、冲突检测、过期和回滚。
5. 继续验证知识库管理员运行游标和重复运行保护，人工复核界面另行设计。
6. 增加 Worker 轨迹评测、成本预算和失败恢复指标。
7. 定义项目级访问控制和敏感信息保留策略。
8. 验证自动读取、定时触发和常驻运行后再减少人工步骤。

## 下一步

2026-11-20 用户已批准 [聊天与任务闭环专项设计 v0.2](./JARVIS%20聊天与任务闭环机制设计%20v0.2.md) 落地。现行运行入口加入按意图识别、规划逐步价值审查、plan_revision、环节证据与人工按 ID 恢复。知识收尾可由已批准任务策略在明确验收后触发，验收后先确认本任务笔记选择，未答不自动整理，仅同意本地时准备候选，具体知识库写入及正式发布仍受批准范围约束；此前“仅手动触发”的描述按本补充更新。职责分工、技能不持有整体状态、预算不清零和画像不得推断不变。详细步骤见 [任务闭环规程](../docs/task-lifecycle.md)，本地演练不等同跨会话/外部服务验证。

1. 按真实 Skill、证据和人工确认条件补充正式经验，不为数量目标填造条目。
2. 扩展验证“知识库管理员整理 → 人工复核 → 管家查询 → Worker 工作包”的实际复用质量。
3. 用历史高频任务验证频率排序和经验复用收益。
4. 单独评审首次安装、自动化和恢复设计；文档对齐不授权启用这些能力。
