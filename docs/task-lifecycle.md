# 聊天、任务、人工恢复与收尾运行规程

2026-11-20 用户认可专项设计并明确要求落地。本规程与 AGENTS.md 配套，是当前项目协作规则；不是后台调度器或宿主原生配置。设计依据见[专项设计](../架构方案/JARVIS%20聊天与任务闭环机制设计%20v0.2.md)。

## 入口与任务卡

只在意图不明时问聊天还是任务。明确任务直接起草契约；闲聊不建卡，出现交付意图时切换；恢复旧任务不新建空卡。问候、状态查询和当前契约反馈不另建审批。

### 任务中出现明显偏离内容：先确认关联性

2026-11-20 用户明确要求：任务进行中（含任务讨论、规划与执行），若新增内容明显偏离当前目标，且无法看出对任务完成的用途，先问：“这部分内容确实与当前任务的完成有关吗？”可简述当前目标与新增内容的关联缺口，避免自行断言用户在闲聊。

- 按语义、当前契约和已说明的用途判断；换话题、举例或询问相似项目不自动代表无关。有明确用途的补充、澄清、纠正、状态询问，以及明确的暂停、取消或切换指令，直接按其含义处理，不重复确认。
- 用户确认相关：按其说明用于当前任务；若实质改变目标、范围、验收、预算或组织授权，按契约变更流程处理。
- 用户确认无关：若尚未说明，询问是临时闲聊还是另起任务，以及原任务是否继续；已有明确选择直接遵循。明确建立新任务后才按新任务入口处理，不因偏题本身建卡、建对话或改标题。
- 用户未答：不展开新增分支，不擅自取消、改写原任务或启动新任务；保留当前进度，仅继续原授权内不受影响的工作。确实依赖关联性答复的后续动作等待答复，沉默不视为切换授权。

本条用于确认内容与当前任务的关系，不给任务内普通补充增加额外审批。

### 闲聊转为潜在任务：先确认模式

用户在聊天中提出建设动作（搭建、开发、制作、整理、研究等），并指向具体产物或要达成的结果，即使说“要不要一起……有兴趣吗”，也应识别为潜在任务。按语义与上下文判断，不靠单个关键词；不要把潜在任务擅自归为继续聊天，也不要未经确认启动实施。

主动回应：“Andy，这里可能从闲聊转成一个建设任务了。你想先聊可行性，还是正式启动？启动的话，我会先起草任务卡，与你明确目标、验收、范围和预算。”模式确认可以和少量关键问题一起提出，但不能用市场/技术参数提问代替它。

- 先聊：保持讨论，后续出现新的启动意图再确认，不每轮追问。
- 启动：建立待澄清/待复核卡片，记录启动依据，再补全契约；首次建卡即按下节分流，执行仍遵守事前复核。
- 明确执行指令：无需重复二选一，直接起草契约。
- 未答：只继续不依赖启动授权的讨论，不标已启动、不改会话标题。
- 假设/角色演示/测试：可在演示中展示应有的模式确认；真实任务仍是当前测试，不实际创建被演示的业务项目。

| 输入例子 | 应有响应 |
|---|---|
| “一起搭一个股票分析 Agent，有兴趣吗？” | 识别转折，询问先聊可行性还是正式启动 |
| “请搭建股票分析 Agent，先给我任务卡” | 直接创建契约草案，集中确认缺口 |
| “股票分析 Agent 为什么会出错？” | 正常解释，不因出现 Agent 就建卡 |
| “先聊聊想法，暂时不做” | 继续聊天，不启动 |
| “上述只是测试” | 记录测试反馈，不启动股票项目 |

用 [任务模板](../templates/task.md) 创建 `.local/tasks/<task_id>/contract.md`。简单任务可简写，需跟踪和跨中断恢复则须落盘。用户明确建立真实新任务后首次建卡即创建并绑定专属对话；恢复时核对卡片与真实活动，不信标题。

完整任务先填目标、验收矩阵、范围、输入、授权、预算和停止条件；管家提出默认值供契约复核，不让用户填长表。约 20 分钟是收敛检查点，不是默认总上限；完整任务另定主动执行上限及截止/等待条件，不把“有时间”当无限预算。

## 新任务与专属对话绑定（2026-11-20 用户批准）

一项真实新任务首次建卡，创建一个同名专属对话；待澄清/待复核不妨碍先分流。用户明确提出新任务是触发依据；只讨论假设、模板样例、测试或补录旧卡不触发。已批准任务内的普通修订、返修与规则修改不递归生成新任务卡。临时Worker仍用委派机制，不建立用户侧任务聊天。

1. **先核对绑定**：读取任务卡的 task_thread_id 和 session_binding_status；已有绑定先查证并复用，不凭标题另建。source_thread_id 与专属绑定分开登记。
2. **先记意图**：落盘任务ID、来源对话、项目、目标名称、creation_attempt_id、授权与查证方法，状态置“创建中”。先查询正式项目列表，再用返回的项目ID在同一项目、本地环境创建；未明确要求不新建worktree，不覆盖用户模型设置。
3. **传递交接**：用 [交接模板](../templates/task-session-handoff.md) 携带卡片绝对路径、task_id、契约/计划修订、原始需求摘要、已批准/待批准范围、必要输入及下一步。接收方将其视为已有任务续作，绝不再次建卡/建会话。首次仅只读核对并简短确认，未经复核不启动业务执行。
4. **核验并绑定**：保存创建工具回执，记录正式对话ID及返回的host/project信息；独立回读标题和所属项目/工作目录，必要时用正式改名工具修正新对话标题。核验后将唯一专属ID写入任务卡并保留来源关联。接收方读卡并正确复述任务才记交接确认；源会话此后停止推进该任务业务，避免双重执行。
5. **分开报告验证**：工具创建成功、名称/项目读回一致、接收上下文确认、侧边栏视觉显示分别记录。无可用界面核验时只报告前三项实测，侧边栏记未验证，不宣称检查过界面。
6. **恢复与异常**：同一任务修订、返修、恢复复用已绑定对话。创建结果未知先按回执/列表/尝试记录查证，不重复创建；已创建但命名/卡片关联失败时修复原实例。绑定对话不可用先核实，再取得替代入口的具体授权，保留旧新关联；工具缺失或项目不明则记阻塞并报告，不把原聊天改名当作新建。

原对话保留，不自动归档、删除或强行中断。由其他聊天收到的恢复请求只做定位与交接，不新增第二个主执行入口。规则分流与业务事前复核独立；创建新对话不扩大授权或预算。本规程依赖管家与宿主工具，未实现后台自动监听或原子会话锁。

## 规划与价值审查

计划绑定 contract_revision 与独立的 plan_revision。逐步记录目的、验收关联、依赖、产出用途、完成证据、执行者和恢复方法。

执行前自审：是否必要；删掉会损失什么；产出由谁使用；能否直接完成或复用；能否验证/恢复；委派收益是否覆盖沟通整合成本。每步留下保留、合并、删除或延期及简短理由。没有用途的中间报告不保留，必要验证/恢复记录也属于真实价值。默认直接执行，不以步骤/Agent 数量评价质量。

计划未通过先修订。内部调整只升计划修订；影响目标/验收/范围/预算/组织授权时升契约修订并复核。标记受影响步骤和后继失效/待重验；有效独立结果可保留，旧 Worker 不得覆盖新产物。

## 关键记录与安全写入

经复核选用长路径执行的任务，按 [长路径执行规程](task-loop.md) 使用本地运行器记录领用、验收和续作决定。

卡片是当前状态入口，事件表或 events.jsonl 保留历史。任务小则合并一张卡，不强制分文件。每步至少记录 task_id、契约/计划修订、step_id、attempt_id、时间、执行者/实例、输入基线、动作、结果、输出/回执、验证、失败与预算、下一步。

有成本/副作用的动作前先写意图、对象、授权及查证方式，工具返回即记已执行/未执行/未知，验证后才标已验证。缺成功记录不等于动作未发生。外部幂等键仅在服务真实支持时使用，不承诺精确一次执行。

每个阶段、交接、等待、变更、暂停及交付保存检查点；突发退出可能缺最后记录，恢复必须查事实。记录不可写时暂停依赖可靠记录的副作用动作。单一管家写当前卡；更新前核对基线，同目录唯一临时文件校验后替换，证据使用排他创建的 run_id/attempt_id；有人工修改或并发冲突先停止覆盖。无跨文件事务、跨进程锁或零丢失保证。

环节状态：待执行、执行中、已执行待验证、已验证、失败、阻塞、结果未知、已失效、已跳过。跳过要解释依赖是否仍满足。卡片最后显示执行中但实际活动无法确认时，标注需恢复核对，不猜测完成。

## 人工恢复

用户可说“JARVIS，恢复任务 <task_id>”或提供卡片路径；可在原聊天或新聊天进行。任务 ID 在任务目录可定位，不依赖原聊天存活。

1. 读最新契约、计划、记录、检查点、产物及失败账本。多个候选只问必要定位；卡片缺失说明缺口，不假造历史。
2. 核对旧工具、Worker、外部作业和写入者。活动不明时不重复派发或启动冲突写入；不为恢复主动中断他人任务。
3. 核验产物、输入版本和外部回执。已验证且仍有效的结果保留；变化标待重验；未知副作用先查证，无法查明交决策。
4. 检查授权、依赖、截止时间、父任务剩余预算与重试。恢复不重置额度；未知用量不填 0、也不假定额度充足。
5. 选择首个安全、依赖已满足的未完成步骤；记录恢复批次、保留/失效步骤及原因。原范围内继续，无须重复批准全部契约；超预算或实质变化才复核。
6. 交付时保留卡片路径、修订、最后验证步骤、未知动作、产物、剩余预算/未知项、阻塞及下一核对动作。

已验收任务收到恢复请求先区分查看、返修、新需求；已取消任务明确重启后仍复查旧授权。只做人工唤起，不承诺退出应用后继续执行或自动恢复。

## 验收、变更与知识收尾

自检和用户验收分开；沉默、继续讨论或礼貌回应不自动算通过。原验收项未达是返修，新增目标修订契约或另立关联任务；同类失败在父任务累计，不借换人/重派/恢复清零。

业务明确验收后，若本任务没有明确笔记选择，先集中询问一次：“是否整理任务笔记：不整理、仅本地总结，还是整理到知识库？”已有本次明确选择不重复问。一般流程认可或“确认关闭”不代替笔记选择；未回答不自动生成总结/候选，业务可记已验收，收尾记待选择，不宣布全部完成。必要执行记录、证据与检查点仍保存。选择本地整理时，才在本任务 closure/ 准备总结与必要候选；无新增内容不凑三篇。选择不整理则记已跳过；只说“不入知识库”时禁止写库，也不因此默认新增本地笔记，现有本地材料保留。

知识库写入必须有任务卡中的收尾授权：触发条件、来源白名单、目标文件/目录、可新增或允许修改字段、预算、输入基线和冲突处理；有这些具体批准可在验收后接续执行，无须重复请示。没有就只在已获本地整理同意时交本地候选。用户说不用整理则跳过。用 [知识请求模板](../templates/knowledge-run-request.json) 实例化限定任务，不扫描其他聊天、项目或全库，不自动生成日报周报。

project 对应工作记录/任务总结，domain 对应 wiki/主题，resource 对应 wiki/参考资料。正式 wiki 覆盖、规则、正式经验和长期能力仍提交具体差异批准；候选不自动升级。写入检查来源、去重、链接和基线漂移，单写入流程，保护人工编辑。

## Skill 决策与结束

读取相关且已确认的画像；当前明确要求优先。工作职责未知则标未知，候选/猜测不参与；只有会改变判断时才询问，不自动新增画像字段。依输入目标稳定性、实际工作相关性、预期复用和维护成本记录：无需、已有 Skill、模板/脚本、局部/判断方法 Skill、新 Skill 或待证据。

输入/目标变化大不强制 SOP；稳定的是澄清和验收方法时可提判断型 Skill。记录依据来源、稳定部分、收益成本和边界，收尾集中报告一次，有价值才询问制作。制作是关联任务，读取真实 skill-creator、回放验证、人工确认发布；拒绝或延期不阻塞业务关闭。

关闭前核对：关联任务已验收/明确停止或转交；新增要求有去向；无活动执行或未知副作用；产物与恢复入口已交付；收尾完成/跳过/转交；Skill 决定有记录。明确报告“可以结束”，不自动归档或永久删除。

## 本次验证边界

文件与规则由主会话执行，不构成强制控制。落地检查及本地恢复演练记录在任务 `JV-20261120-TASK-MODE` 的 implementation-01；恢复演练只使用本地测试副本。跨聊天恢复、真实外部服务与多写入者保护仍须真实任务观察，不能由文件存在推导验证通过。
