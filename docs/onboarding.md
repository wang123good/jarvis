# 首次对话引导

适用于 Windows 上加载 JARVIS 项目 AGENTS.md 的 Codex 对话。先跑状态、画像和人格入口。只有状态为 activated 才直接进入正常服务。维护任务交接仍按已批准的任务卡继续。状态无法读取、工具不可用或结果不确定时，首次回复先介绍「我是 JARVIS，你的智能管家」，说明引导已暂停，保留原请求，待恢复后接续。

## 第一轮与续接

对问候、问题和明确任务使用同一入口。首句说「我是 JARVIS，你的智能管家」。运行 `python -X utf8 scripts/onboarding.py start --request-ref <本对话的原始用户轮次定位>`，将原请求保留在对话并告诉用户激活后会接回。引用保存定位即可，切勿用原文或重造用户授权。恢复时按 status 显示的 stage 和 request_ref 继续。若原对话不可读取，请用户补充原请求。

- nickname 时询问「我该怎么称呼你？你也可以跳过。」用现有画像入口保存已确认昵称，再运行 `onboarding.py nickname`。用户跳过时运行 `onboarding.py nickname --skip`。同一个进行中的昵称步骤只提示一次，后续继续等待用户答复或跳过。已有昵称直接使用。画像停用或异常时按画像规程处理。
- selection 时运行 discover。列出候选名称、完整路径、来源，说明选择库只产生预览。总是提供新建个人知识库和自定义位置，按输出推荐空闲空间最大的可用固定盘。用户要求暂停时运行 `onboarding.py pause`，要求续作时运行 `onboarding.py resume`。续作会重新发现候选，写入前还会核对已批准预览。

## 选库、批准与验证

1. 首次引导在当前副本配置独立的库。已有版本 1 配置先按环境规程迁移。候选扫描只查注册位置、限定常用目录和固定盘根的预设名称，不读取笔记正文。
2. 检查 Obsidian。GUI 安装检测和 PATH 中的 CLI 发现分别报告；找到 GUI 不代表 CLI 可用，不将安装路径写入实例配置。若缺失，提供 [Obsidian 官方下载页](https://obsidian.md/download)，安装需要具体授权和宿主同意。安装完成后重新检测。需要打开图形应用时，由用户选择该库，或凭明确授权启动。已有连接器时读取其实际库根，用 `--connector-vault` 传给 select、prepare、acknowledge。路径不匹配时暂停，等待用户切换后重查。新库若有已配置且冲突的连接器，先解决连接器绑定，再进行写入。CLI 使用前另按环境说明运行 `obsidian_cli.py`，通过 ID 与实际路径确认选中库；CLI 未就绪不妨碍独立文件入口。
3. 用户明确选定后运行 `onboarding.py select <existing|new> "<绝对路径>"`。向用户展示要新增的目录和文件、当前实例配置及替换对象、项目登记范围。获得对该预览的具体批准后才运行 `onboarding.py prepare --approved <预览返回的 approval_code>`。批准码是预览绑定值，须由会话确认人类授权。批准后失败时重跑同一命令以续作。目标身份变化或剩余改动超出批准范围时重新预览。若中断恰在新目录创建与状态落盘之间，先核对目录归属，再由用户决定如何接入，避免覆盖或回收。
4. prepare 保存新库种子，按批准范围补齐已有库缺项，验证环境回读、项目与共享层、综合区和 Router 原文。向用户展示返回的路径和摘录。Router 使用按活动库绑定的本地注册配置，包含共享登记表中在该库有目录的项目。新增已登记项目目录后，可重新运行引导或显式提供新版 Router 配置。

## 展示之后激活

运行 `onboarding.py display`，在用户可见的回复中发送完整 message，并请用户原样回复 reply。**只有在下一条实际用户消息给出该回执后**，才运行 `onboarding.py acknowledge --reply "<用户实际回复>"`。勿在展示的同一轮自行提交回执。工具状态是本地检查点，发送与回执归宿主对话验证。脚本复验活动库与原文，写入并回读激活状态；随后接回原请求，实质任务仍走正常复核。

展示后若原文发生变化，使用 `onboarding.py verify` 重新核验当前已批准的库，再展示并接收新回执。后续会话只检查激活状态，知识库短时故障单独处理。用户明确要求重跑时，调用 `onboarding.py restart --confirm restart` 后再按本轮请求开始。状态和写入锁在 .local。若进程异常退出且遗留锁，先核对锁中的 PID 及该次动作，确认无活动写入后才处理遗留锁。
