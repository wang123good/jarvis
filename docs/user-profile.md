# 本地用户画像

2026-11-19 用户批准本地单用户方案 B：首次仅询问昵称，后续按确认规则积累协作偏好。根目录 `up.json` 是唯一活动画像入口；不依赖 Obsidian 路径，本版不处理多端同步。

## 初始化

每次新会话首次回应前、实质任务开始时，运行 `python scripts/read_profile.py --status`。读取器只读，不创建文件或覆盖异常数据。

- `needs_initialization`：礼貌询问“你好，碳基伙伴，很高兴与你一起工作。你希望我怎么称呼你？我会将这个称呼保存在本地，方便以后与你交流。”
- 用户回答后，以 `up.example.json` 为结构创建根目录 `up.json` 并保存昵称；回答即为本地保存称呼的授权，无需再次确认。不得从账号、目录名或旧画像猜昵称。
- 用户跳过时使用临时称呼“碳基伙伴”，继续任务，同一会话不重复询问；不把临时称呼写成已确认昵称。
- `ready`：自然使用昵称，根据当前任务筛选相关偏好。
- `disabled`：不应用画像，也不自动启动初始化。用户要求重新启用时再修改。
- 读取失败：保留原文件、说明异常，停止应用画像；不自动重建覆盖。
- Obsidian vault、Skill 根目录和其他机器绝对路径不属于画像；通过 `scripts/setup_environment.py` 写入 `.local/environment.json`。画像只需按已确认偏好引用知识库别名，不保存本机目录。

## 后续维护

人格表达另由 `python -X utf8 scripts/persona.py --persist` 接入：新会话、昵称初始化后和已批准互动偏好纠正后重算，每轮按 AGENTS.md P01 选择情境。它不增加初始化问卷或人格选择，不修改 up.json；画像缺失、停用、异常或无相关偏好时使用沉稳默认。collect_candidates=false 时只应用已有正式偏好并冻结派生状态写入。人格总开关关闭时跳过该适配路径，原画像初始化/确认流程保持不变。详见 [人格规程](persona.md)。

1. “以后叫我……”直接更新昵称；“请记住……”等明确长期保存指令可直接写入已确认偏好，并简短告知。当前任务的临时要求不自动变成长期偏好。
2. 观察到的倾向仅记录为 `candidates`，集中呈现具体内容及适用范围；用户确认后移入 `preferences`。候选不参与行为指导，不因出现次数多而自动批准。
3. 偏好字段：`id`、`statement`、`scope`（当前仅 JARVIS）、`source`（简短原话和当前任务/会话定位，不依赖外部绝对路径）、`recorded_at`、`status`；正式条目另含 `approved_at`。日期采用 Asia/Shanghai 的 ISO 日期。`status` 为 approved / paused / revoked；候选为 candidate。
4. 仅应用 approved 且 scope=JARVIS 的条目；适用场景在 statement 中写清楚，遇到冲突先按当前要求执行，再核对长期条目。画像不授予额外权限。
5. 用户可查看、纠正、删除条目，清空画像或关闭积累。关闭整个画像使用 `enabled=false`，保留文件；仅要求停止积累时设 `collect_candidates=false`，继续应用已有偏好。用户要求删除的数据不另存永久备份。
6. 不推断职业、专业背景、人格或敏感信息，不自动扫描历史聊天。只保存必要的简短来源，不保存完整会话。

## 安全写入与分发

### 每轮操作

- 回复前只检查当前用户轮次。用户主动说明的长期工作场景、明确协作偏好或纠正可作为证据。讨论中的选项、一次性指令、助手复述及未经用户陈述的推断不计。用稳定的条目 ID 合并同义事实，使用可定位的原始用户轮次 ID 作为事件。同一句话重放复用原事件 ID。每条每轮只计一次。
- 用 UTF-8 JSON 通过 stdin 调用 `python scripts/update_profile.py`。观察传入 `action=observe`、`id`、`event`、`statement`、`source`、`date`。场景写进 statement，来源只保留必要短摘与定位。优先使用现有条目的 ID。旧条目基线计数 1，新增计数按去重证据数计算。
- 用 `python scripts/update_profile.py --proposals` 查看可复核项。正式维度最多 20 条（含暂停和撤销记录），昵称另计。正式条目按计数降序，同分保留文件顺序。未满可补入，满额时仅候选计数严格大于末位的 110% 才提示。每次回复集中呈现相关提案及证据，向用户呈现后用 `shown` 记录候选 ID 与 target。相同候选和末位组合在用户决定前只显示一次。用户选择 `keep` 或 `defer` 后，至少新增两条独立证据才再次提示相同组合。
- 按用户决定调用 `approve`、`replace` 或 `merge`，均传候选 `id` 和 `date`，替换和合并传正式 `target`，合并另传用户认可的 `statement`。可用 `correct`（statement、source）、`pause`、`resume`（date）、`revoke`、`delete` 和 `settings` 执行明确授权的修改。明确要求记住的偏好可观察后立即按授权批准，满额时由用户决定合并或替换。
- 需要画像协助理解时，先用 `python scripts/read_profile.py --index` 获取精简索引，按场景选 ID，再用 `--select ID ...` 获取最多 5 个已批准条目。仅需初始化状态时用 `--status`。索引用于匹配场景，选定条目才参与当前任务。以当前明确要求为先，只在画像改变重要判断时说明依据。
- 更新器用独占锁串行化使用该入口的写入，并在替换前重读基线。锁文件已存在时先查证是否有活跃写入者。异常中断遗留锁需查证后处理。独占锁约束使用该入口的写入者。

### 运行边界

每轮语义检查、来源定位和场景选择由加载本项目规则的 JARVIS 执行。读取器及更新器负责结构验证与确定性计算。当前机制依赖活动对话按规程调用本地工具。现有对话可能需要新开 JARVIS 项目对话以加载更新后的入口规则。

更新器先读取最新文件，校验新结构，在同一目录排他创建唯一的 `up.json.<随机标识>.tmp`，关闭后核对基线并用 os.replace 替换目标。初始化使用排他创建，防止覆盖已存在文件。失败时清理本次临时文件。

`up.json` 及其临时文件由 `.gitignore` 排除；公开仓库只提供空白 `up.example.json`。发布前检查暂存区，避免泄露个人画像。

旧文件已迁往库外，位置见 [归档索引](archive-index.md)。旧 `profile.json`、`candidates.json`、`changes.jsonl`、schema 与批准文件保留为历史证据，不再读取、不自动迁移，也不作为新用户默认偏好。现有用户偏好需逐项重新确认；通用治理规则继续由 AGENTS.md 负责。历史文件仍可能存在于 Git 历史，本次未清理公开历史。

## 验证边界

读取器检查结构并筛选已确认条目；候选采集、礼貌询问、确认与安全写入由管家遵循指令完成，不是后台服务。新会话初始化、用户纠正与持续积累的实际行为需在真实使用中继续验证。
